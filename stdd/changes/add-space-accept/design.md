# 设计：空格接受建议词和联想词

## 方案

**组词**：空格一直是「提交高亮项」（`[composition.08]`），变的只是高亮一开始放在哪：

| 条件（开关开启） | 初始高亮 |
|---|---|
| 原样是已知词（词表或系统拼写检查认识） | 原样 |
| 原样不是已知词，拼写检查有纠错 | 第一个纠错词（候选第二位） |
| 原样不是已知词，只有补全没有纠错 | 原样 |

候选窗显示的高亮和空格会提交的内容始终一致，所以不是「悄悄改字」：用户按空格前能看到要提交什么。每次组词变化（加字母、退格）都按上表重新算初始高亮；用户用方向键移动过高亮后，以用户选的为准。回车提交高亮项，所以开启时回车也提交纠错词；Esc 仍提交原样，用来临时保留拼写。

整句翻译用的「有效词」原来就是「原样不认识时取第一个建议词」，和新的初始高亮一致，不用改。

**联想**：开启时，联想状态下按空格 = 接受高亮联想词 + 空格并继续联想，和 Tab 相同；没有联想词（只为显示译文留着候选窗）时照旧把空格交给应用。关闭时空格收起联想并交给应用（现有行为）。

**设置**：`Preferences.spaceAcceptsSuggestion`，默认 `true`，UserDefaults 键 `spaceAcceptsSuggestion`；设置窗加开关「空格接受建议」，说明文字「拼错时空格提交纠错词；联想时连按空格接受联想词」。

## 备选与取舍

| 方案 | 好处 | 代价 | 结论 |
|---|---|---|---|
| 空格总是提交第一个建议词 | 最省键 | 补全也会被空格接受，打生词、人名、代码标识符会被改成别的词 | 不采用 |
| 只在有纠错时把高亮移到纠错词（本方案） | 行为和 iOS 键盘一致；高亮所见即所得 | 补全仍要 Tab | 采用 |
| 联想时单击空格就接受联想词 | 更快 | 用户只是想打空格时会被插入联想词 | 不采用；联想状态本身就是「刚打过空格」，再按一次空格才接受 |
| 默认关闭 | 不改变老用户习惯 | 维护者要的就是更顺手，默认关等于没做 | 默认开启 |

## 数据 / 配置 / 协议变化

新增设置项 `spaceAcceptsSuggestion`（Bool，默认 true）。没有数据文件格式变化。

## 兼容与迁移

旧设置里没有这个键，读取时取默认值 true。bootstrap 变更里描述「空格提交原样」的 `[composition.07]` 前提改为「关闭空格接受建议」（bootstrap 尚未归档，直接在它的增量里改，并在它的 design-adjustments 里记一笔）；`[settings.01]` 的默认值清单不动，新开关的默认值由 `[settings.09]` 单独约束；`[settings.04]` 的「四个开关」改为「五个开关」。

## 风险与回滚

- 系统拼写检查对专有名词、缩写给出纠错，开启后按空格会被改掉：高亮可见，按 Esc 或 → 移回原样即可；也可以关掉开关。
- 回滚：关掉开关即回到旧行为，不需要回退代码。
